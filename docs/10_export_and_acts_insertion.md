# 10 — Exporting the models and where they plug into ACTS

Docs 08 and 09 end with two PyTorch checkpoints. ACTS is C++ and runs
without Python or LibTorch, so the models travel as a small binary blob and
are evaluated by a hand-written forward pass. This document covers the
blob, the C++ that reads it, and the two places in the Combinatorial
Kalman Filter where the gate and the value function are called. All of the
C++ lives in `acts_patches/` and is copied into a pinned ACTS source tree
at build time; ACTS itself is not forked.

## Export

```
python scripts/export_weights.py --checkpoint models_v4/gate_maj/gate_model.pt --standardization ckpt \
    --calibration models_v4/gate_maj/calibration/platt_params.json --output weights_v4/maj/gate.bin --model-type gate
python scripts/export_weights.py --checkpoint models_v4/value_t3_maj/value_model.pt --standardization ckpt \
    --calibration identity --output weights_v4/maj/value.bin --model-type value
```

`--standardization ckpt` takes `mu`/`sigma` from the checkpoint (where the
trainers store them); `--calibration identity` writes a no-op Platt
(a = 1, b = 0) for the value function. The blob (`WeightBlob.hpp` reads it;
`tests/test_export_weights.py` round-trips it):

```
"CCKF"                    magic
uint32  version = 1
uint32  n_features        26 gate / 11 value
uint32  n_hidden          128
uint32  n_layers          hidden layers: 3 gate / 2 value
float32 mean[n_features]  standardisation
float32 std[n_features]
float32 a0, a1, b0, b1    occupancy-conditional Platt (identity for value)
per layer, hidden then head:  float32 weight[out × in] row-major, float32 bias[out]
```

The feature *names* are not in the blob. The C++ builds the full 26 (or 11)
in the order of `cckf.features.GATE_FEATURES` / `VALUE_FEATURES` and nothing
checks that order at load time, so a change to either list must be made in
both `cckf/features.py` and the C++ builder in the same commit.

**Ablated models.** A checkpoint trained with `--feature-groups` or
`--drop-features` (doc 07) has fewer input columns. The exporter reads its
`feature_names`, inserts a zero column in the first layer for every dropped
feature, and writes mean 0 / std 1 for it, so the blob is always full
width: the C++ computes the feature and multiplies it by nothing.
Deploying an ablation therefore needs no rebuild. A windowed value model
(12 features) is refused, because the C++ builds 11.

Put a `provenance.json` next to promoted blobs (checkpoint path, training
job, AUCs, calibrator, code hash); `cckf_handoff/weights_v3/maj/` is the
template.

## The C++ library (`acts_patches/cckf/`)

Header-only, seven files:

| File | Role |
|---|---|
| `WeightBlob.hpp` | parses the blob into vectors |
| `MlpInference.hpp` | the forward pass: standardise, `n_layers` × (matrix-vector + SiLU), head; `forwardBatch` does one matrix-matrix product per layer for all candidates on a surface; `calibrate(logit, log n_window)` applies the Platt form a(x)·z + b(x). One instance per thread; the parity test `tests/test_mlp_inference.cpp` checks it against a PyTorch logit at 10⁻⁵ |
| `CckfFeatures.hpp` | `buildGateFeatures(...)`: the 26 gate features in `GATE_FEATURES` order from the innovation, the cluster, the sensor and the branch context; `chi2LogOdds(chi2)`, which mirrors `features.chi2_log_odds` exactly (`tests/test_chi2_logodds.cpp`) |
| `CckfMeasurementSelector.hpp` | the gate: scores every candidate on a surface and returns the accepted ones |
| `CckfBranchStopper.hpp` | the value function: builds the 11 state features and decides Continue / StopAndKeep / StopAndDrop |
| `SensorLookup.hpp` | pitch and thickness per volume from the digitisation JSON |
| `CckfTimers.hpp` | per-event counters and timers that end up in `timing.csv` |

Compile the two parity tests without ACTS:

```
clang++ -std=c++17 -O2 -Iacts_patches/cckf tests/test_mlp_inference.cpp -o /tmp/t_mlp && /tmp/t_mlp
clang++ -std=c++17 -O2 -Iacts_patches/cckf tests/test_chi2_logodds.cpp -o /tmp/t_lo && /tmp/t_lo
```

Their fixtures (`tests/fixtures/gate_test*.bin`, `chi2_logodds_ref.bin`)
are regenerated by `pytest tests/test_export_weights.py tests/test_features.py`.

## The two insertion points

ACTS' CKF exposes two delegates, function objects it calls at fixed points
in its loop (doc 03). `CckfTrackFindingAlgorithm` (in
`acts_patches/ActsExamples/TrackFinding/`) is a copy of ACTS' own
`TrackFindingAlgorithm` with those two delegates connected to our code and
nothing else changed: same propagator, same Kalman updater, same track
containers, same two-way finding and track selection.

### 1. `measurementSelector` → the gate

Called once per surface with every measurement on that surface as a
candidate track state. `CckfMeasurementSelectorAdapter::select` in the
algorithm file gathers the branch context (a backward walk over the branch
counting `n_hits`, `n_holes`, `n_seq_holes` and `step_k`, reading η, q/p and
the material since the last hit) and the sensor properties, then
`CckfMeasurementSelector::select`:

1. For every candidate, one Eigen pass computes the residual, the
   innovation covariance S = V + H C Hᵀ (per candidate, with its own V)
   and χ².
2. **Box pre-filter.** Candidates outside `gateWindowNSigma` × √S on either
   axis are dropped before scoring; `n_window` is the count that survive.
   This reproduces the expansion's window (doc 06), so the gate only sees
   the distribution it was trained on. With it off, ACTS hands over every
   hit on the surface, with χ² up to 10⁵, which is how the first
   deployment failed (log 2026-08-20). If nothing survives the surface is a
   hole (`hole_window_failure` in the timing CSV).
3. **Features and score.** `buildGateFeatures` per candidate, one
   `forwardBatch` for the surface, then `calibrate(logit, log n_window)`:
   the calibrated probability P(same particle).
4. **Accept** the candidates with P ≥ `gateThreshold` (τ_g), sorted by
   score, at most `gateMaxCandidates`; each accepted candidate becomes a
   branch. None accepted: a hole (`hole_gate_failure`). The selector never
   marks outliers.

Not applied: `gateChi2Ceiling` is plumbed from the YAML but unused (removed
from the decision in 822d655 so the gate, not a χ² cut, decides).

### 2. `branchStopper` → the value function

Called after every track state is appended (measurement, hole or material).
`CckfBranchStopperWrapper` first updates four per-branch columns that the
value features read: `cckf_step_k` (+1 per call), and at measurement states
`cckf_sum_gate_logodds` += `chi2LogOdds(χ²)`, `cckf_min_gate_logodds` =
min. The log-odds come from the accepted hit's χ², not from the gate's
logit, because that is what `build_value_cache.py` accumulates (the
mismatch fixed on 2026-09-04). Then `CckfBranchStopper::operator()`:

1. Fewer than `minMeasurementsBeforePrune` (3) measurements: Continue.
2. Build the 11 features from the state's parameters and covariance, the
   track's hole counters and the four columns. `x0_accumulated` is 0: the
   TODO in the wrapper was never done (doc 09 says how to neutralise it).
3. `prob = sigmoid(forward(features))`; if `prob < valueThreshold` (τ_v),
   stop: `StopAndKeep` when the branch has at least `minMeasurementsForKeep`
   (6) measurements, else `StopAndDrop`.

The two constants are C++ defaults, not exposed to the YAML.

### What runs when a weight path is empty

| `cckf_gate_weights` | `cckf_value_weights` | selection | stopping |
|---|---|---|---|
| set | set | gate | value function |
| set | `""` | gate | `ClassicalBranchStopper`: ACTS' own hole/outlier caps from the track selector config, per-technology `maxPixelHoles` / `maxStripHoles` |
| `""` | set | ACTS `MeasurementSelector` with the YAML χ² cuts | value function (its log-odds still accumulate from χ²) |
| `""` | `""` | χ² cuts | classical caps |

`ClassicalBranchStopper` is a copy of the `BranchStopper` in ACTS'
`TrackFindingAlgorithm.cpp`; it was added on 2026-09-14. Before that a
run without value weights had **no** in-flight branch stopping, so
"gate-only" numbers from before that date are not comparable to anything.
Doc 11 uses these four modes.

### Config keys, YAML to C++

| YAML (`digi_and_reco.py`) | C++ `Config` | default |
|---|---|---|
| `cckf` | routes to `CckfTrackFindingAlgorithm` instead of `addCKFTracks` | false |
| `cckf_gate_weights`, `cckf_value_weights` | `gateWeightsPath`, `valueWeightsPath` | "" |
| `cckf_gate_threshold`, `cckf_value_threshold` | `gateThreshold`, `valueThreshold` | 0.5, 0.1 |
| `cckf_gate_max_candidates` | `gateMaxCandidates` | 10 |
| `cckf_gate_window_nsigma` | `gateWindowNSigma` | 0 (off; always set it) |
| `cckf_gate_chi2_ceiling` | `gateChi2Ceiling` | 15 (unused) |
| `cckf_digi_config` | `digiConfigPath` (sensor lookup) | `digi_config` |
| `cckf_timing_output` | `outputTimingPath` | none |

Every C++ config field must also appear in the pybind list inside
`scripts/apply_cckf_integration.sh`; a field missing there binds silently
to its default. That script is the whole integration: it copies the seven
headers and the two algorithm files into the ACTS tree, adds the sources
to the TrackFinding `CMakeLists.txt`, and appends the Python bindings.

## Building after a C++ change

```
salloc -N1 -C cpu -q interactive -t 00:45:00 -A atlas
./scripts/build_cckf_nersc.sh --install        # rsync the changed headers, rebuild two targets, 1 to 2 min
exit
```

or, without an interactive node, `sbatch scripts/nersc/apply_and_build.sbatch`
(re-runs the integration script and the same build). The first build is
`scripts/nersc/bootstrap_build.sbatch` (`NERSC.md` §7). `CLAUDE.md` keeps
the table of build errors met so far; the one that bites most often is
capturing an Eigen expression from a track-state accessor with `auto`
instead of `.eval()`, which compiles and then crashes on the first event.

## Timing and diagnostics

With `cckf_timing_output: timing.csv` the algorithm appends one row per
event: seeds, tracks, nanoseconds and call counts for feature building,
gate inference, value inference and measurement selection, the gate's
accept/reject counts and mean scores, NaN-feature counts, candidates
removed by the pre-filter, and the three hole causes. `timing_traces.csv`
next to it records the first 100 tracks' per-candidate features and scores,
the closest thing to the parquet rows the C++ can show. ACTS' own
per-algorithm wall clock goes to `timing.tsv` (comma-separated despite the
name). `scripts/extract_metrics.py` reads all three plus the performance
files into one JSON.

## Checking parity end to end

The offline scorer `scripts/diagnostics/score_branch.py` (doc 08) computes
gate probabilities for a branch from the parquet with the Python feature
code; `timing_traces.csv` shows what the C++ computed for the same
candidates in a run on the same event. Agreement to the 10⁻⁴ level on
`chi2` and the score, for the same window, is the check that the two
feature builders still match. There is no automated test for this yet.
